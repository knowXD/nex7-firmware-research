# 可实现清单 v2（2026-11-15，基于深入分析之后）

> 早期那份（ROADMAP_v1）是"立项"阶段的想象；这份是**扒完固件之后**能落地的。
> 最大的变化不是"多了几个功能"，而是**工作方式的跃迁**。

---

## 一、三个工作方式级的跃迁（比功能更重要）

### 1. 刷一次桩，之后全部走 /setting 迭代

**发现**：场景模块由 \`libtestcmd_scn.so\` 通过 \`dlopen("/usr/scenario/<名>.so")\` + \`dlsym("scenario_run")\` 加载。
我们做的**委托桩**可以在被调用时 \`dlopen("/setting/orig_video.so")\`，把调用转给原模块。

**于是可以这样**：

```
第一次：刷一个"只做转发 + 记日志"的桩进 /usr/scenario/xxx.so（一次刷机）
之后：  所有实验代码都放 /setting/xxx_exp.so，通过 shell push 进去
        重启 → 桩 dlopen 新文件 → 立刻生效
```

⇒ **不用每次改代码都重新打包刷固件**。这是这个项目最重要的一次效率跃迁。

> **[证据等级] 这里要标清楚**：`dlopen("/usr/scenario/<名>.so") + dlsym("scenario_run")` 是在
> `libtestcmd_scn.so`（相机自带的**测试命令** `bin/scenario.elf` 用的加载器）里确认的 [静态]。
> **相机运行时（sen.elf）是否走同一个加载器，目前是 [推测]**——不过所有 scenario 模块都是
> 同一种被 dlopen 的 .so、导出同一个符号，共用加载器的可能性很高。
> 这一条要等相机活了、第一次刷桩时验证。
风险：桩本身坏掉会黑屏（和 dmode 一样），所以桩要极小、可回滚。

### 2. NAND 备份/恢复闭环

工具已经齐了：\`nandump2\`（读分区）、\`dump_check.py\`（体检 + 找 /setting）、\`setting_patch.py\`（改 dmode 等）。
**意义**：任何后续改动都有"后悔药"，不用再靠"换主板"兜底。

### 3. 场景钩子通用化

不只是视频：任何 \`scenario/*.so\` 都可以用同一套"桩 + 委托"替换。
可钩的点包括 \`CAMERA_SCN_EE_START_STOP\`（拍摄启停）、\`MPR_SCN_FORMAT\`（格式化）、\`CAMERA_SCN_MOVIE_REC_START\`（录像开始）。

## 三、确认做不到（分析之后才敢说死）

- 装 Android / 移植 Android：内核 binder/ashmem/logger 全为 0，需重编内核且无板级源码；
- 改 UI / 菜单：uxc 私有格式；
- 免拆救砖：所有启动标志在 NAND 上；
- 机内堆栈（星轨/多帧合成）：需要 ISP 帧缓冲接口，没有入口。

## 四、等相机复活后的第一件事

不是刷功能包，而是：

1. 串口拿 shell → 验证 \`/setting\` 可写、\`/usr\` 只读；
2. 刷一个**委托桩**（最小、只记日志）→ 确认能加载、能转发；
3. 从此进入"改 /setting 就能迭代"的循环。

---

## 五、一句话

早期我们想的是"能改哪些数字"；现在真正拿到的是**"一个可迭代的注入架构 + 一条备份退路"**。
功能是副产品，这两样才是资产。
